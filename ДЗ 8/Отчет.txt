Описание проекта и ключевой сущности
В рамках задания была выбрана сущность Review (отзыв) — типичный элемент сервиса анализа пользовательских мнений. Отзыв содержит:

идентификатор (id);
текст (text);
рейтинг (rating, от 1 до 5);
дата создания (createdAt);
идентификатор продукта (productId).
Сценарии использования:

Чтение: частое (тысячи раз в минуту) — получение отзывов по productId;
Запись: умеренная (сотни в минуту) — добавление новых отзывов;
Фильтрация: по дате («все отзывы за последнюю неделю») и рейтингу («только с оценкой ≥4»);
Связи: требуется связь с продуктом, но без сложных JOIN (достаточно productId);
Транзакции: не критичны — потеря одного отзыва допустима;
Гибкость схемы: важна — возможны дополнительные поля (например, tags, photos) в будущем.
Для сравнения были реализованы два хранилища:

Реляционная БД: PostgreSQL через Spring Data JPA;
Нереляционная БД: MongoDB через Spring Data MongoDB.
Оба хранилища интегрированы в одно Spring Boot-приложение с возможностью переключения через профиль (jpa / mongo).

Сложность реализации
PostgreSQL (JPA)
Требуется чёткая схема: все поля определены в @Entity;
Для фильтрации — метод репозитория:
findByProductIdAndCreatedAtAfter(...);
Индексы задаются через @Index;
При добавлении нового поля — миграция БД (Liquibase/Flyway).
MongoDB
Схема гибкая: новые поля добавляются без изменений в коде;
Фильтрация через @Query или метод:
findByProductIdAndCreatedAtAfter(...);
Индексы задаются через @CompoundIndex;
Вложенные структуры (например, tags: ["полезно", "быстро"]) хранятся естественно.
Вывод по сложности:
MongoDB проще в разработке при нестабильной схеме; PostgreSQL требует больше boilerplate, но обеспечивает строгую целостность.

Выявленные узкие места
PostgreSQL:
— Задержки при генерации @GeneratedValue (sequence);
— Более высокая нагрузка на CPU при сложных фильтрациях;
— Требуется настройка connection pool (HikariCP).
MongoDB:
— Отсутствие транзакций усложняет согласованность при связанных операциях;
— Потребление памяти выше при большом объёме данных.
Архитектурные компромиссы и вывод
Для сценария «отзывы пользователей» требования таковы:

высокая частота записи и чтения;
гибкость схемы важнее строгой целостности;
транзакции не требуются;
фильтрация простая (по 1–2 полям).
MongoDB лучше подходит по следующим причинам:
✅ Выше throughput при записи;
✅ Гибкая схема ускоряет развитие продукта;
✅ Проще масштабируется горизонтально;
✅ Достаточная производительность при фильтрации.

PostgreSQL оправдан, если:
— Требуется строгая согласованность (например, финансовые данные);
— Сложные связи между сущностями (много JOIN);
— Отчёты с агрегацией по множеству таблиц.

Принятые компромиссы:
— Отказ от ACID в пользу гибкости и скорости;
— Доверие к идемпотентности клиентов (повторная отправка отзыва не создаёт дубликатов);
— Использование productId как внешнего ключа без реального FOREIGN KEY.

Заключение
Сравнение показало, что выбор СУБД должен основываться на сценариях использования, а не на популярности. Для высоконагруженных, гибких систем с простыми запросами (как сервис отзывов) MongoDB обеспечивает лучшую производительность и удобство разработки. Для систем с критичной целостностью данных (банки, бухгалтерия) предпочтителен PostgreSQL.

В данном проекте рекомендуется использовать MongoDB как основное хранилище отзывов, с возможностью миграции к гибридной архитектуре (Polyglot Persistence) в будущем.
