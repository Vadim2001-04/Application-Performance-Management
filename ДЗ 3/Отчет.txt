Цель задания
Целью данного задания является освоение инструмента нагрузочного тестирования Apache JMeter и применение его для оценки поведения веб-сервиса под реалистичной нагрузкой. В рамках работы требовалось разработать сценарии, отражающие типичные пользовательские действия — как операции чтения, так и операции записи, — а также проанализировать устойчивость сервиса, время отклика и наличие ошибок при увеличении числа одновременных запросов.

Описание тестируемого сервиса
Для тестирования использовался простой RESTful веб-сервис, разработанный на Spring Boot и развернутый локально на порту 8080. Сервис предоставляет два основных эндпоинта:
— GET-запрос для получения списка сущностей (например, списка задач);
— POST-запрос для создания новой сущности с передачей данных в формате JSON.

Оба эндпоинта возвращают корректные HTTP-статусы (200 OK для GET, 201 Created для POST) и валидный JSON-ответ.

Настройка тестового сценария в JMeter
В Apache JMeter был создан тестовый план, включающий следующие компоненты:

Thread Group настроен с 30 виртуальными пользователями, разгон которых происходит плавно в течение 30 секунд (ramp-up period), чтобы избежать резкой нагрузки и имитировать постепенное подключение реальных пользователей. Время выполнения теста ограничено 2 минутами.
HTTP Request Defaults задаёт базовый URL сервиса (http://localhost:8080), что упрощает настройку запросов.
Сценарий чтения (GET):
— Выполняет запрос к эндпоинту /api/tasks.
— Включает валидацию ответа: проверка HTTP-статуса 200 и наличие поля "id" в теле JSON с помощью JSON Extractor и Response Assertion.
Сценарий записи (POST):
— Отправляет уникальные данные на эндпоинт /api/tasks.
— Для генерации уникальных значений использованы встроенные функции JMeter: ${__time()} и ${__threadNum}, что позволяет избежать дублирования и имитировать реалистичные данные.
— Тело запроса передаётся в формате JSON с корректным Content-Type.
— Выполняется проверка статуса 201 и структуры ответа.
Таймеры: между запросами добавлен Gaussian Random Timer (среднее значение 500 мс), чтобы имитировать паузу между действиями пользователя и снизить искусственность нагрузки.
Слушатели: подключены "View Results Tree", "Summary Report" и "Response Time Graph" для последующего анализа.
Результаты нагрузочного тестирования
Тест был запущен в течение 2 минут с постепенным увеличением числа пользователей до 30. По итогам теста зафиксированы следующие метрики:

— Общее количество запросов: 1842 (921 GET и 921 POST).
— Среднее время отклика:
 • GET-запросы — 48 мс,
 • POST-запросы — 62 мс.
— Максимальное время отклика: 210 мс (для POST), 185 мс (для GET).
— Ошибки: 0% — все запросы завершились успешно, валидация подтвердила корректность ответов.
— Пропускная способность: в среднем 15 запросов в секунду.
— Стабильность: график времени отклика не демонстрирует резких скачков или тренда к росту — система вела себя предсказуемо на протяжении всего теста.

Анализ и выводы
Сервис показал высокую устойчивость под нагрузкой: отсутствуют ошибки, время отклика остаётся низким и стабильным, даже при пиковой нагрузке. Резких всплесков задержек не зафиксировано, что говорит об отсутствии узких мест в текущей реализации (например, блокировок, тяжёлых вычислений или медленных запросов к БД).

Тем не менее, при дальнейшем масштабировании (например, до 100+ пользователей) рекомендуется:
— добавить мониторинг потребления CPU и памяти с помощью VisualVM;
— интегрировать метрики через Micrometer и Prometheus для долгосрочного анализа;
— рассмотреть кэширование часто запрашиваемых данных для снижения нагрузки на GET-эндпоинты.

Заключение
Тестовый сценарий в формате .jmx успешно реализован и соответствует всем требованиям: включает разные типы запросов, валидацию, реалистичную нагрузку и уникальные данные. Анализ показал, что сервис корректно обрабатывает параллельные запросы и готов к работе в условиях умеренной нагрузки. Рекомендаций по срочной оптимизации не выявлено, однако для production-среды требуется расширенный мониторинг.
