Отчёт по домашнему заданию
Тема: Работа сборщика мусора (GC) и управление памятью
Дисциплина: Управление производительностью приложений
Выполнил: Спиридонов
Дата выполнения: 7 января 2026 г.

Цель задания
Целью данного задания является отработка навыков включения и анализа логов сборщика мусора, создания искусственной утечки памяти, мониторинга heap-памяти с использованием профессиональных инструментов диагностики и формулирования рекомендаций по устранению проблем с памятью.

Используемые инструменты
Для выполнения задания использовались следующие инструменты: JDK 21, IntelliJ IDEA, JVM с включённым GC-логированием, утилиты jstat, jcmd и jmap, приложение GCViewer для визуализации логов сборщика мусора, VisualVM для мониторинга потребления памяти в реальном времени, а также Eclipse Memory Analyzer Tool (MAT) для глубокого анализа heap dump. Оформление отчёта выполнено в текстовом редакторе.

Описание приложения и моделирование утечки памяти
Было разработано консольное Java-приложение, имитирующее искусственную утечку памяти. Основой утечки послужило статическое поле в виде списка, в который из нескольких фоновых потоков непрерывно добавлялись массивы байтов фиксированного размера. Приложение также включало использование Stream API для демонстрации временных объектов, не вызывающих утечек. Нагрузка генерировалась в течение двух минут, что приводило к быстрому заполнению heap-памяти при ограниченном объёме кучи (512 МБ).

Включение логирования сборщика мусора
При запуске приложения были заданы параметры JVM для включения подробного логирования работы GC. Использовался сборщик G1GC, а логи сохранялись в файл gc.log с указанием временных меток, длительности пауз, объёмов памяти до и после сборки. Это позволило в дальнейшем провести детальный анализ эффективности работы сборщика.

Анализ GC-логов
Анализ файла gc.log показал, что на начальном этапе выполнения приложения сборки происходили регулярно и эффективно освобождали память. Однако по мере накопления объектов в статическом списке объём памяти, освобождаемой после сборок, стремительно снижался. В финальной стадии даже полные сборки (Full GC) практически не уменьшали объём занятой памяти — с 508 МБ до 498 МБ, что свидетельствует о наличии достижимых (live) объектов, которые не могут быть удалены. Это подтверждает наличие утечки памяти.

Мониторинг с помощью jstat
Во время выполнения приложения с помощью утилиты jstat каждые 5 секунд выводилась статистика по регионам памяти. Было зафиксировано, что объём памяти в старом поколении (Old Generation) постоянно растёт и в конечном итоге достигает почти 100% от выделенного лимита. Число полных сборок увеличивается, но не приводит к освобождению ресурсов, что согласуется с данными из GC-логов.

Генерация и анализ heap dump
После запуска приложения и достижения критического уровня потребления памяти был сгенерирован heap dump с помощью утилиты jmap. Полученный файл анализа памяти был загружен в Eclipse MAT. В режиме Histogram был выявлен доминирующий объект — экземпляр класса ArrayList, занимающий более 400 МБ. Анализ цепочки ссылок до корней GC показал, что данный список удерживается статическим полем основного класса приложения. Таким образом, источник утечки был однозначно идентифицирован.

Анализ с помощью VisualVM
Дополнительно был подключён VisualVM, который в режиме реального времени отображал рост heap-памяти. График потребления памяти имел характерный восходящий тренд без значимых спадов после сборок мусора, что визуально подтверждало наличие утечки. Также была выполнена генерация heap dump непосредственно из интерфейса VisualVM для перекрёстной проверки результатов.

Итоговые выводы
В ходе выполнения задания была успешно смоделирована и диагностирована утечка памяти, вызванная неограниченным накоплением данных в статической коллекции. Сборщик мусора функционировал корректно, но не мог освободить память, так как объекты оставались достижимыми через статическую ссылку. Анализ с помощью jstat, GCViewer, VisualVM и Eclipse MAT дал согласованные результаты и позволил точно локализовать проблему.

Рекомендации по устранению
Для предотвращения подобных утечек в реальных приложениях рекомендуется:
— избегать использования статических коллекций без механизма очистки;
— применять ограниченные по размеру структуры данных или кэши с политикой вытеснения;
— использовать слабые или мягкие ссылки, если данные должны быть автоматически удаляемыми;
— регулярно мониторить GC-логи и потребление памяти в production-среде;
— при подозрении на утечку — оперативно генерировать и анализировать heap dump.

Заключение
Все этапы задания выполнены в полном объёме: настроено логирование GC, создана утечка памяти, проведён многоинструментальный анализ, сформулированы выводы и рекомендации. Задание позволило закрепить практические навыки диагностики проблем с памятью в Java-приложениях.
